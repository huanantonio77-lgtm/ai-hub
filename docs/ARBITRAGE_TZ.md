# Техническое задание: бот для межбиржевого криптоарбитража

## 1. Цель проекта

Разработать программного торгового бота для поиска и исполнения 
межбиржевого арбитража на спотовом рынке.

Бот должен:

- получать актуальные котировки и стаканы нескольких криптобирж;
- находить расхождения цен;
- рассчитывать потенциальную чистую прибыль с учётом всех расходов;
- одновременно размещать ордера на покупку и продажу;
- контролировать частичное исполнение и ошибки;
- автоматически останавливать торговлю при превышении рисков;
- собирать статистику для последующей оптимизации параметров.

На первом этапе бот работает **только со спотом, без маржинальной торговли 
и фьючерсов**. Биржи предоставляют REST- и WebSocket-интерфейсы, а для 
тестирования некоторые из них имеют тестовые среды. <citation 
src="1,3,4"></citation>

---

## 2. Рекомендуемый состав MVP

Для первой версии:

- 2 биржи;
- 3–10 торговых пар;
- только USDT-пары;
- только заранее размещённые балансы на обеих биржах;
- только лимитные или агрессивные IOC-заявки;
- без автоматического вывода средств;
- без кредитного плеча;
- без самостоятельного изменения риск-лимитов;
- сначала режим симуляции, затем небольшая реальная сумма.

Пример торговых пар:

```text
BTC/USDT
ETH/USDT
SOL/USDT
XRP/USDT
```

Конкретный набор пар должен задаваться в конфигурации, а не быть зашитым в 
коде.

---

## 3. Режимы работы

Бот должен иметь четыре режима:

### 3.1. `RESEARCH`

Только загрузка данных и анализ возможностей.

Бот:

- получает котировки;
- рассчитывает потенциальную прибыль;
- не выставляет ордера;
- сохраняет все найденные ситуации.

### 3.2. `PAPER`

Симуляция торговли.

Бот имитирует:

- отправку заявок;
- частичное исполнение;
- комиссии;
- проскальзывание;
- задержку;
- отказ API;
- недостаток ликвидности.

### 3.3. `TESTNET`

Торговля в тестовой среде биржи, если она доступна.

### 3.4. `LIVE`

Реальная торговля с установленными ограничениями:

- максимальная сумма одной сделки;
- дневной лимит убытка;
- список разрешённых пар;
- список разрешённых бирж;
- запрет вывода средств через API.

## 4. Источники данных

Для каждой биржи необходимо реализовать отдельный адаптер.

### Публичные данные

Получать через WebSocket:

- best bid;
- best ask;
- объём на лучших уровнях;
- обновления стакана;
- сделки;
- серверное время;
- sequence number, если биржа его предоставляет.

Через REST получать:

- первоначальный snapshot стакана;
- список торговых пар;
- ограничения по минимальному ордеру;
- шаг цены;
- шаг количества;
- комиссии;
- доступные балансы;
- открытые ордера;
- историю исполнений.

WebSocket нужен для оперативных обновлений, а REST — для начальной 
синхронизации, исторических данных и восстановления состояния после 
разрыва соединения. Локальный стакан необходимо пересобирать после 
пропущенных сообщений или нарушения последовательности обновлений. 
<citation src="4,5"></citation>

### Поддерживаемые биржи

Названия бирж должны задаваться конфигурацией. На уровне MVP можно 
подключить две площадки, имеющие:

- публичный WebSocket;
- приватный WebSocket или REST API для ордеров;
- доступ к балансу;
- sandbox/testnet либо режим paper trading;
- понятные торговые ограничения.

Внутри программы нельзя использовать напрямую уникальный формат одной 
биржи. Нужен единый внутренний интерфейс:

```python
class ExchangeAdapter:
    async def get_markets(self): ...
    async def get_order_book(self, symbol): ...
    async def get_balances(self): ...
    async def place_order(self, order): ...
    async def cancel_order(self, order_id): ...
    async def get_order_status(self, order_id): ...
    async def get_fees(self, symbol): ...
```

## 5. Нормализация данных

Каждая биржа может использовать разные обозначения:

```text
BTCUSDT
BTC/USDT
XBT/USD
```

Внутри системы использовать единый формат:

```text
base_asset = BTC
quote_asset = USDT
symbol = BTC/USDT
```

Для каждой пары хранить:

```json
{
  "symbol": "BTC/USDT",
  "price_tick": 0.01,
  "quantity_step": 0.00001,
  "min_quantity": 0.0001,
  "min_notional": 10,
  "base_asset": "BTC",
  "quote_asset": "USDT"
}
```

Цена и количество должны храниться в `Decimal`, а не в обычном `float`, 
чтобы избежать ошибок округления.

## 6. Логика поиска арбитража

Для каждой пары и каждой комбинации бирж:

```text
Биржа A: цена продажи = best bid
Биржа B: цена покупки = best ask
```

Потенциальная валовая разница:

\[
P_{\text{gross}} =
\frac{Price_{\text{sell}} - Price_{\text{buy}}}
{Price_{\text{buy}}}
\]

Чистая прибыль должна рассчитываться с учётом:

- комиссии покупки;
- комиссии продажи;
- ожидаемого проскальзывания;
- сетевой комиссии, если нужен перевод;
- funding fee, если используются деривативы;
- резерва на задержку исполнения;
- возможных комиссий за конвертацию;
- минимального требуемого запаса прибыли.

Формула:

\[
P_{\text{net}} =
V_{\text{sell}} -
V_{\text{buy}} -
F_{\text{buy}} -
F_{\text{sell}} -
S_{\text{buy}} -
S_{\text{sell}} -
C_{\text{other}}
\]

Где:

- \(V_{\text{buy}}\) — фактическая стоимость покупки;
- \(V_{\text{sell}}\) — ожидаемая стоимость продажи;
- \(F\) — комиссии;
- \(S\) — проскальзывание;
- \(C_{\text{other}}\) — прочие расходы.

Условие входа:

```text
net_profit_percent >= min_profit_percent
```

Например:

```yaml
min_profit_percent: 0.25
safety_buffer_percent: 0.10
max_slippage_percent: 0.08
```

Реальная сделка разрешается только если:

```text
ожидаемая прибыль >
комиссии +
проскальзывание +
резерв риска +
минимальная прибыль
```

## 7. Проверка ликвидности

Нельзя рассчитывать прибыль только по лучшей цене в стакане.

Бот должен пройти по нескольким уровням стакана и рассчитать среднюю цену 
исполнения для заданного объёма.

Например, для покупки:

```text
ask 1: 60 000 — объём 0.01 BTC
ask 2: 60 020 — объём 0.02 BTC
ask 3: 60 050 — объём 0.05 BTC
```

Если требуется купить 0,05 BTC, нужно рассчитать средневзвешенную цену, а 
не использовать только `ask 1`.

Требования:

- минимальная глубина стакана;
- минимальный объём на нужной цене;
- максимальная доля объёма от доступной ликвидности;
- отказ от сделки, если ожидаемое проскальзывание выше лимита.

Пример:

```yaml
max_orderbook_consumption_percent: 15
max_slippage_percent: 0.08
min_liquidity_usdt: 5000
```

---

## 8. Требования к балансам

Так как перевод активов между биржами во время сделки может занимать много 
времени, бот должен поддерживать заранее распределённые остатки:

```text
Биржа A:
- BTC
- USDT

Биржа B:
- BTC
- USDT
```

Перед открытием сделки бот проверяет:

- достаточно ли USDT на бирже покупки;
- достаточно ли BTC на бирже продажи;
- не заблокированы ли средства в открытых ордерах;
- не превышен ли лимит использования баланса;
- разрешена ли торговля конкретным активом.

Пример:

```yaml
max_balance_usage_percent: 20
min_quote_balance: 100
min_base_balance: 0.001
```

Запрещено использовать автоматический вывод средств в MVP.

## 9. Исполнение сделки

Арбитражная операция состоит из двух связанных ордеров:

```text
Leg 1: купить BTC на бирже A
Leg 2: продать BTC на бирже B
```

Состояния операции:

```text
DETECTED
VALIDATING
SUBMITTING
PARTIALLY_FILLED
FILLED
HEDGING
COMPLETED
FAILED
EMERGENCY_EXIT
```

### Основной сценарий

1. Найдена возможность.
2. Повторно проверены цены.
3. Проверены балансы.
4. Проверена ликвидность.
5. Рассчитана чистая прибыль.
6. Сформированы два ордера с уникальным `client_order_id`.
7. Отправлены заявки.
8. Отслеживается исполнение через приватный WebSocket или REST.
9. При полном исполнении фиксируется результат.
10. При проблеме запускается процедура компенсации.

### Защита от одностороннего исполнения

Главный риск — один ордер исполнился, а второй нет.

Возможные действия:

- отменить неисполненный ордер;
- уменьшить или повторить второй ордер;
- немедленно захеджировать позицию;
- закрыть операцию по рынку с ограниченным убытком;
- остановить бота после нескольких таких случаев.

Пример:

```yaml
order_timeout_ms: 1500
max_partial_fill_percent: 20
max_hedge_loss_percent: 0.15
stop_after_failed_hedges: 3
```

---

## 10. Типы ордеров

На MVP поддержать:

- `LIMIT`;
- `IOC` — исполнить сразу или отменить остаток;
- `MARKET` — только для аварийного выхода.

Для обычной торговли предпочтительнее использовать лимитные или 
IOC-заявки, если это соответствует API биржи. Рыночные ордера могут 
привести к неконтролируемому проскальзыванию.

Каждый ордер должен содержать:

```json
{
  "client_order_id": "arb-20261002-000001-leg-a",
  "exchange": "exchange_a",
  "symbol": "BTC/USDT",
  "side": "BUY",
  "type": "IOC",
  "quantity": "0.01000",
  "limit_price": "60000.00",
  "strategy_id": "cross_exchange_v1"
}
```

## 11. Управление рисками

Обязательные ограничения:

```yaml
max_trade_notional_usdt: 100
max_daily_loss_usdt: 20
max_open_operations: 1
max_position_time_seconds: 10
max_api_errors_per_minute: 5
max_price_age_ms: 300
max_clock_difference_ms: 500
max_consecutive_losses: 5
```

Бот должен аварийно остановиться, если:

- цена устарела;
- WebSocket потерял соединение;
- стакан повреждён или имеет пропущенную последовательность;
- обнаружено расхождение баланса;
- одна из бирж не отвечает;
- превышен дневной убыток;
- превышено количество ошибок;
- биржа изменила торговые ограничения;
- превышено время нахождения незахеджированной позиции.

Нужна кнопка или команда:

```text
EMERGENCY_STOP
```

Она должна:

1. запретить новые сделки;
2. отменить открытые ордера;
3. показать незахеджированные позиции;
4. при необходимости закрыть их по заранее заданному сценарию.

## 12. Самообучение и ИИ

> **Инвариант s156 (R1, R2, R5):** «ИИ» в этом разделе = **локальная ML stage 3+**, обучаемая на Mac. **LLM-API запрещены** (OpenAI, Anthropic, HF). Runtime stage 1–2 работает только на правилах и математике. См. `docs/ARCHITECTURE_RULES.md`.

ИИ не должен напрямую принимать неконтролируемые решения о торговле.

### Что можно передать модулю оптимизации

- выбор минимального спреда;
- оценку фактического проскальзывания;
- прогноз вероятности исполнения;
- оптимальный размер заявки;
- оценку задержки каждой биржи;
- определение пар с наилучшей ликвидностью;
- обнаружение необычного поведения рынка.

### Что ИИ не может менять самостоятельно

- максимальный размер сделки;
- дневной лимит убытка;
- разрешение на вывод средств;
- максимальное плечо;
- список бирж;
- аварийные правила;
- отключение логирования;
- лимит незахеджированной позиции.

### Процесс обучения

```text
Сбор данных
    ↓
Формирование признаков
    ↓
Разделение на train/validation/test
    ↓
Обучение
    ↓
Backtest с комиссиями и задержками
    ↓
Paper trading
    ↓
Проверка на новом периоде
    ↓
Ручное или ограниченное автоматическое утверждение
```

ИИ должен менять параметры только через конфигурацию, а новая конфигурация 
должна пройти:

- проверку допустимых диапазонов;
- backtest;
- paper trading;
- проверку на независимом периоде;
- сравнение с текущей версией.

Нельзя переобучать модель после каждой сделки. Это создаёт риск подгонки 
под случайный шум.

## 17. Безопасность

API-ключи:

- хранить только в Secret Manager или зашифрованных переменных окружения;
- не записывать в логи;
- не передавать ИИ-модели;
- ограничить по IP, если биржа поддерживает такую возможность;
- отключить разрешение на вывод средств;
- создать отдельные API-ключи для каждой биржи;
- использовать отдельные субаккаунты;
- регулярно менять ключи.

Пример:

```env
EXCHANGE_A_API_KEY=...
EXCHANGE_A_API_SECRET=...
EXCHANGE_B_API_KEY=...
EXCHANGE_B_API_SECRET=...
TRADING_MODE=PAPER
```

- состояние бота;

- последняя цена;
- количество найденных возможностей;

- остановке бота;
- превышении дневного убытка;

- незахеджированной позиции;
- несоответствии балансов;
- превышении задержки;
- серии неудачных сделок.

## 19. Тестирование

Обязательные тесты:

### Unit-тесты

- расчёт комиссии;
- расчёт чистой прибыли;
- округление цены;
- округление количества;
- расчёт средней цены по стакану;
- проверка минимального ордера;
- обработка частичного исполнения.

### Интеграционные тесты

- подключение к API;
- получение стакана;
- отправка тестового ордера;
- отмена ордера;
- получение баланса;
- восстановление после разрыва WebSocket.

### Сценарии отказа

- цена устарела;
- биржа не отвечает;
- исполнена только покупка;
- исполнена только продажа;
- неправильный баланс;
- превышен rate limit;
- повторное сообщение;
- потерян фрагмент стакана;
- задержка ответа API.

### Backtest

В тесте обязательно учитывать:

- реальные комиссии;
- исторический стакан;
- задержку;
- проскальзывание;
- частичное исполнение;
- недоступность биржи;
- ограничения по объёму;
- период, на котором модель не обучалась.

---

## 20. Критерии готовности MVP

MVP считается готовым, если:

- бот поддерживает минимум две биржи;
- умеет восстанавливать стакан после разрыва;
- корректно рассчитывает чистую прибыль;
- учитывает реальные комиссии и ограничения торговых пар;
- не открывает сделку при устаревших данных;
- умеет обрабатывать частичное исполнение;
- работает в режимах `RESEARCH`, `PAPER` и `LIVE`;
- имеет аварийную остановку;
- API-ключи не имеют права вывода средств;
- все операции записываются в базу;
- тесты покрывают расчёт прибыли и отказ одной из ног;
- перед реальными средствами бот не менее нескольких дней работает в 
paper-режиме.

## 21. Этапы разработки

### Этап 1 — симулятор

- модель стакана;
- расчёт прибыли;
- комиссии;
- виртуальные сделки;
- отчёты.

### Этап 2 — сбор рыночных данных

- WebSocket двух бирж;
- локальные стаканы;
- нормализация символов;
- запись данных.

### Этап 3 — сканер возможностей

- поиск спредов;
- расчёт ликвидности;
- фильтрация по рискам;
- уведомления без торговли.

### Этап 4 — paper trading

- симуляция задержек;
- частичное исполнение;
- виртуальный PnL;
- проверка отказов.

### Этап 5 — testnet

- реальные тестовые заявки;
- сверка статусов;
- отмена и повтор;
- проверка аварийных сценариев.

### Этап 6 — минимальная реальная торговля

- одна пара;
- одна операция одновременно;
- минимальная сумма;
- строгий дневной лимит убытка.

### Этап 7 — модуль оптимизации

- сбор статистики;
- оценка проскальзывания;
- подбор порогов;
- контролируемая проверка новых параметров.

Главное правило ТЗ: **сначала строится надёжная система исполнения и 
контроля риска, а затем добавляется самообучение**. Иначе ИИ может 
оптимизировать красивую, но нереальную прибыль на исторических данных, а 
реальные сделки будут сталкиваться с задержками, неполным исполнением и 
комиссиями.
